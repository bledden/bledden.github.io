<p>The <a href="/blog/four-months-upstreaming-consumer-blackwell/">previous post</a> was about getting other people&#x27;s code to run on this chip. It was four months of dispatch fixes and attention kernels upstreamed into flash-attention, FlashInfer, vLLM, SGLang, CUTLASS, and Triton, so that <code>pip install</code> and serve became a thing you could do on a DGX Spark. That work answered whether the open stack runs on consumer Blackwell. This post is about the part that came after, and the reason it came after. Porting the stack is what showed me exactly where the toolchains still fall short on this chip, and <code>sm121-kernels</code> is the library I wrote to fill those gaps. It is flash attention, GEMM, and gated-delta-net kernels for SM121, written as hand-written PTX, assembled to SASS by <code>ptxas</code> at build time, and dispatched from Rust with no runtime dependency beyond the CUDA driver.</p>
<p>The thesis is one sentence, and it cuts both ways: <strong>hand-written PTX wins where the compiler toolchain has a gap, and loses where the toolchain is mature.</strong> The FP8 section is the win. The BF16 section is the loss, measured as carefully as the win.</p>
<p>A note on terms before the marketing instinct kicks in. &quot;Consumer Blackwell&quot; is not one chip. The flagship attention work of the last year (FlashAttention 4, CUTLASS&#x27;s CuTe DSL kernels, ThunderKittens 2.0) targets <code>sm_100</code>, the datacenter Blackwell, and is built on the <code>tcgen05</code> matrix instructions and a tensor-memory hierarchy that the consumer part does not have. SM121 allows 99 KB of shared memory per thread block where SM100 allows about 227, exposes the SM80-generation <code>mma.sync</code> warp-level MMA where SM100 has WGMMA and <code>tcgen05</code>, gives 256 registers per thread, and has a 1×1×1 cluster shape, which means no multicast TMA. It is a different chip wearing the same brand, a point <a href="https://www.backend.ai/blog/2026-02-is-dgx-spark-actually-a-blackwell">backend.ai&#x27;s teardown</a> and gau-nernst&#x27;s tcgen05 walkthrough both make in detail, and one I learned the hard way in the previous post by arguing the opposite in a pull request and getting corrected. Every kernel decision below is downstream of those constraints.</p>
<h2 id="hand-written-ptx-and-why">Hand-Written PTX, and Why</h2>
<p>There is a spectrum of how close to the metal you write a GPU kernel. CUDA C++ is the common floor. CuTe DSL and Triton sit above it as kernel generators that emit PTX for you. PTX is the virtual ISA below all of them, and below PTX is SASS, the actual machine code the hardware runs. Almost everyone targeting SM121 writes near the top of that spectrum. I went down to PTX, for two reasons.</p>
<p>The first is that there is nowhere lower to go. SASS is where the final scheduling and register-bank decisions land, but no open assembler exists for Blackwell SASS (CuAssembler, the one community SASS assembler, stops at SM86), so you cannot hand-write or patch it. PTX is the lowest level you can actually author. From PTX, <code>ptxas</code> still makes the final scheduling and register-allocation calls, so the craft is not controlling every instruction. It is shaping the PTX to coerce <code>ptxas</code> toward the SASS you want, reading the result back with <code>nvdisasm</code>, and iterating. This is the same approach gau-nernst used to reach near-peak BF16 on the 5090 with Ampere-era instructions, and it is the only lever you have on a chip with no SASS assembler.</p>
<p>The second reason is the gap. On a chip the flagship toolchains skipped, their code generation has holes. The sharpest is that CUTLASS&#x27;s CuTe DSL cannot lower the FP8 MMA instruction on SM120 at all, tracked as CUTLASS issue <a href="https://github.com/NVIDIA/cutlass/issues/3044">#3044</a> and still open as of this writing. When the compiler backend can&#x27;t emit the instruction your hardware has, &quot;write better C++&quot; doesn&#x27;t help. You drop to the level where you can emit it yourself.</p>
<p>The cost is real. Hand-writing PTX gives up the compiler&#x27;s software pipelining, its register allocation, and its instruction scheduling, and on the paths where those are mature you will lose to them. That is exactly what happens in BF16, later in this post. So this is not a claim that hand-written PTX is a better way to write kernels. It is a claim that it is the right tool for one specific job: shipping the kernel the toolchain has not shipped yet, on hardware it has not caught up to.</p>
<p>The packaging follows from the same minimalism. Each kernel is a <code>.ptx</code> file, preprocessed for shared macros, assembled to a cubin by <code>ptxas</code> at build time, embedded in the binary, and launched through <code>cudarc</code>. The runtime dependency is <code>libcuda.so</code> and nothing else: no CUDA toolkit, no PyTorch, no Python. That is not a performance claim, but it is what makes the kernels drop into a serving binary cleanly, which is where they actually run.</p>

<h3>Maintaining Hand-Written PTX at 296 Files</h3>
<p>The first objection to a hand-PTX library is maintenance, and it&#x27;s a fair one: 296 <code>.ptx</code> files is a lot of assembly. Nearly all of it is written by hand, and that is the work: close to <strong>280 distinct kernels</strong> (<code>.visible .entry</code> points) are what this library is. What a generator takes off your plate is not the kernels themselves, but the <em>variant multiplication</em> stacked on top of a few of them.</p>
<p>Flash attention is the worst offender. One implementation has to ship as a cross-product of causal vs non-causal, GQA, paged KV, split-KV, head dimension, and device-side position, and those variants are nearly identical. The <code>fa_bf16_v3</code> family&#x27;s seven differ by about 6% of their lines; <code>+causal</code> is a 122-line delta on a 1991-line body. Hand-maintaining seven near-copies and keeping them in sync as the shared body changes is exactly the error-prone busywork worth automating, so one <code>.ptx.in</code> template carries the body with the deltas behind <code>#ifdef SPARK_CAUSAL</code> / <code>SPARK_GQA</code> / <code>SPARK_PAGED</code> guards and the build emits each concrete variant. It runs through the same <code>cpp -P</code> preprocessor the macros already use, with no new toolchain.</p>
<p>What the generator does <em>not</em> do is write kernels. The implementation generations (v3 vs v11 vs v21 are different algorithms, not toggles) and every one-off primitive (the GEMMs, MLA, GDN, Mamba-2, the elementwise and training kernels) are authored by hand, instruction by instruction. The generator removes the copy-paste-toggle tax on the handful of families that explode combinatorially. It does not remove the engineering, and the engineering is the bulk of it. The reason the refactor is even safe to do is that <strong><code>ptxas</code> is deterministic</strong>: assembling identical PTX twice yields a byte-identical cubin, so the acceptance gate for a generated variant is <code>cmp</code> on the cubin. A match proves it is the exact kernel the production binary already shipped, bit for bit. A maintainability refactor that can&#x27;t change behavior is the kind you can run against a library serving real traffic.</p>
<h2 id="flash-attention-in-fp8-where-the-compiler-can-t-follow">Flash Attention in FP8, Where the Compiler Can&#x27;t Follow</h2>
<p>SM120 has the FP8 tensor-core instruction. <code>mma.sync.aligned.m16n8k32 ... kind::f8f6f4</code> is in the ISA, the same <code>mma.sync</code> family the BF16 path uses with double the K dimension (32 instead of 16, because the operands are one byte instead of two). What the chip doesn&#x27;t have is a compiler that will emit it. CUTLASS&#x27;s CuTe DSL, the path most people reach for to build a Blackwell FP8 kernel, can&#x27;t lower FP8 MMA for SM120; the gap lives in the closed-source MLIR backend (<a href="https://github.com/NVIDIA/cutlass/issues/3044">#3044</a>). The C++ CUTLASS headers do define the SM120 FP8 MMA atom, so the instruction itself is reachable, but no FP8 flash-attention kernel is built on it and the ergonomic path you would use to write one can&#x27;t compile the MMA. The most-cited consumer-Blackwell flash-attention writeup, <a href="https://gau-nernst.github.io/fa-5090/">gau-nernst&#x27;s speed-of-light FA for the 5090</a>, is BF16 only, with FP8 listed under future work. So the practical state of exact FP8 flash attention on SM120 (the kind that takes FP8 Q/K/V in and runs the softmax inside the kernel) is that the open toolchain mostly doesn&#x27;t produce it. cuDNN does, through its own closed kernels. Below that, you write the MMA yourself.</p>
<p>That is what I did, and it took twelve versions to get right.</p>
<h3>The Climb: 10 to 108 TFLOPS</h3>

<p>The first version was the textbook one: every thread loads its operands, every thread computes, no overlap. 10 TFLOPS, entirely memory-latency-bound. The tensor cores spend most of their time waiting for <code>ld.global</code>. Bigger tiles plus <code>cp.async.cg</code> register-bypass loads (V3) doubled it to 20 by getting more arithmetic per byte fetched and letting loads run ahead of compute. Then I tried TMA (V7), expecting the hardware bulk-copy engine to help, and it <em>regressed</em> to 18. That is the first lesson on the board: <strong>TMA is not free.</strong> A <code>cp.async.bulk.tensor</code> with no compute scheduled to overlap it is just a higher-latency load with more setup; without warp specialization to hide it behind the MMA, the descriptor machinery costs more than it saves. Warp specialization (V11) is what made TMA pay: one DMA warp issues the bulk copies into a shared-memory buffer, four MMA warps consume it, and an <code>mbarrier</code> arrive/wait pair carries the handoff. That producer/consumer overlap brought it to about 30.</p>
<p>Thirty TFLOPS is a respectable warp-specialized FP8 kernel. Getting to 108 took a different kind of move.</p>
<h3>The VT-GMEM Layout</h3>
<p>The FP8 MMA wants its operands in a specific register layout, one lane holding a specific set of the matrix&#x27;s elements, and the naive path pays for that layout twice. The V tile arrives from shared memory in the arrangement the load produced, and the <code>mma</code> instruction expects a different arrangement, so every iteration of the inner loop does a per-thread transpose in registers (shuffles and selects) before it can issue the matmul. At BF16 issue rates you can sometimes hide that. At FP8 rates, where the MMA itself is twice as fast, the transpose stops hiding. It sits on the critical path and it scales with the inner loop, so the faster you make the matmul the more the transpose dominates.</p>
<p>V12c stores V already transposed in global memory, the layout I call VT-GMEM, so the load delivers operands in exactly the arrangement the MMA consumes. The per-thread shuffle disappears entirely. The kernel stops paying a tax it was paying every single iteration, and FP8 throughput jumps to roughly 108 TFLOPS. The transpose moves out of the hot loop and into a one-time layout choice at the boundary. That is the second lesson, and the most important one: <strong>on this chip, layout beats scheduling.</strong> I spent versions V3 through V11 improving how work was scheduled and got from 10 to 30. One change to how the data was laid out got from 30 to 108.</p>

<h3>The Red Herring That Cost a Week</h3>
<p>The VT-GMEM V tile has shared-memory bank conflicts. They show up clearly in Nsight Compute (the L1/TEX pipe is the top throughput limiter at 88% of speed-of-light), and the textbook response is to swizzle the shared-memory layout with an XOR permutation so that the conflicting accesses spread across banks. I wrote the swizzle. It made the kernel slower, and not by a little. The conflicted VT-GMEM layout runs 2.3 to 3.2× faster than the bank-conflict-free swizzled version.</p>
<figure id="ptx-original-02"><a href="/images/consumer-blackwell/ptx-original-02.png" aria-label="Open full-size figure"><img src="/images/consumer-blackwell/ptx-original-02.png" alt="The bank-conflict &#x27;fix&#x27; made it slower. <p>The reason is that the conflicted layout is the one that hands the MMA its operands in the right order. Swizzling to remove the bank conflicts destroys that alignment and reintroduces exactly the per-thread shuffle VT-GMEM existed to delete. The bank conflicts are real, the profiler is right that L1/TEX is the limiter, and paying them is still the fastest design, because the alternative costs more somewhere the profiler&#x27;s top-line number doesn&#x27;t point at. The lesson is one I keep relearning: <strong>the optimization the profiler points you toward can still be wrong; the profiler tells you the truth but not the inference.</strong> The bank-conflict count is a fact; &quot;therefore remove the bank conflicts&quot; is a hypothesis, and on this kernel it was false.</p>
<h3>The Numbers, and the Baseline That Isn&#x27;t There</h3>
<p>DGX Spark (GB10, sm_121a), D=128, non-causal, FP8 e4m3 inputs, CUDA-event median:</p>
<div class="table-scroll"><table><thead><tr><th>Shape</th><th>spark-kernels V12c</th></tr></thead><tbody><tr><td>B=2 H=32 S=2048</td><td>107.5 TFLOPS</td></tr><tr><td>B=2 H=32 S=4096</td><td>94.1 TFLOPS</td></tr><tr><td>B=2 H=32 S=8192</td><td>108.6 TFLOPS</td></tr></tbody></table></div>
<p>Roughly 108 TFLOPS at the ends, with a dip to 94 at S=4096, and this time I ran it down. It is not wave or tile quantization: a clean sweep in 512-token steps puts the neighbors 3584 and 4608 both back near 110, so only S=4096 notches, and the per-element shared-memory bank-conflict rate is identical across the three. The notch has two parts. A few TFLOPS of it is benchmark cache warmth and lifts when I re-run with an L2 flush before each timed launch; the rest, about 12%, survives the flush and tracks the power-of-two stride. The pre-transposed V is stored as a flat [D, B·H·S] buffer, so consecutive D-rows sit B·H·S elements apart; at B=2, H=32, S=4096 that stride is exactly 2¹⁸, a power of two only because B, H, and S are each powers of two, which is the classic setup for memory-channel camping. The neighbors&#x27; B·H·S (with S = 3584 = 2⁹·7 or 4608 = 2⁹·9) isn&#x27;t a power of two, so their rows don&#x27;t alias onto the same channels. I then confirmed it by varying the stride directly. Holding S=4096 fixed and sweeping the head count (which scales B·H·S), the notch appears only when B·H·S lands on a power of two and vanishes one step to either side: H=31 and H=33 both run at ~110 TFLOPS while H=32 drops to ~89, and it is worst at exactly the 2¹⁸ (256 KB) stride, milder at 2¹⁹, and gone at 2¹⁷. So the cause is the stride itself, not S and not the head count. The DRAM channel metric isn&#x27;t exposed on this part to name the exact aliasing, but the behavior is unambiguous and the fix confirms it: padding the V^T row stride off the power-of-two boundary (a +512-element pad in the tensor-map, memory cost ~0.2%, applied automatically whenever B·H·S is a power of two) recovers S=4096 from ~90 to ~110 TFLOPS, the neighbors&#x27; speed. That padding is also the clean single-variable test the head-sweep couldn&#x27;t be (it moves only the stride, leaving shape, work, and grid fixed), so it settles the cause and ships the mitigation in one change. It only bites shapes where B·H·S lands on a power of two. The more interesting part of this section is the column I could not fill.</p>
<p>I went to benchmark the baselines you would reach for, and ran out of baselines. cuDNN 9.19 has a BF16 fused-attention engine for sm_121 and builds one without complaint. Ask it for the FP8 variant and it returns <code>cudnnGraphNotSupportedError: no valid engine configs</code> for smVersion 1210. There is no FP8 fused-attention engine for this chip. CUTLASS&#x27;s CuTe DSL cannot lower the FP8 MMA at all (<a href="https://github.com/NVIDIA/cutlass/issues/3044">#3044</a>). gau-nernst&#x27;s reference is BF16 only. flash-attention&#x27;s SM120 FP8 path is a KV-decode GEMV, not a prefill forward. So the claim is not &quot;fastest,&quot; which would invite a cherry-picking read. It is narrower and, I think, more interesting. As of mid-2026 this is the only exact-FP8-input flash-attention forward I can get to run on sm_121a at all. The vendor library won&#x27;t build one and the dominant open toolchain can&#x27;t compile one. (The cuDNN result reproduces from <code>scripts/bench_cudnn_fp8_fa.py</code>: the BF16 graph builds, the FP8 graph throws.)</p>
<p>One scoping the number needs, because a serving engineer will ask it first. This is a <em>prefill</em> number on a contiguous, pre-transposed V. VT-GMEM works by storing V already transposed in global memory so the load hands the MMA its operands in order, and that layout does not compose with a scattered paged KV cache, where the per-page address computation breaks the contiguous access the transpose relies on. The library&#x27;s paged FP8 kernel is a separate, older (V3-generation) kernel that pays the gather and runs well below this. Decode is a different regime again: a single query against a KV cache is memory-bound, tens of GB/s, and runs its own FP8-KV decode kernel, not this one. So 108 is the compute-bound long-context prefill forward, the throughput that matters when a long prompt lands, and it is explicitly not the number the paged or decode paths run. One more piece of layout accounting, since the 108 rests on V arriving pre-transposed: that transpose is a separate, bandwidth-bound relayout (read V once, write V^T once), not fused into the V-projection&#x27;s store in the current code, so it is additive to the 108 rather than free, though small next to the attention compute. The library also ships a variant that folds the transpose into the kernel through a shared-memory transpose at a lower peak; V12c buys the peak by moving the transpose to the boundary.</p>
<p>FP8 was winnable for exactly the reason BF16, next, is not. The instruction is new enough that the compiler hasn&#x27;t caught up to it on SM120, and &quot;the compiler hasn&#x27;t caught up&quot; is precisely the seam where dropping to PTX pays. You are not out-optimizing a mature toolchain. You are filling a hole it hasn&#x27;t filled yet.</p>

<h2 id="bf16-where-the-toolchain-wins">BF16: Where the Toolchain Wins</h2>
<p>If FP8 is the seam where dropping to PTX pays, BF16 is the place it doesn&#x27;t. The BF16 MMA on SM120 is <code>m16n8k16</code>, the same SM80-era instruction the ecosystem has had for years. The compiler paths for it are mature: CUTLASS&#x27;s CuTe DSL generates well-pipelined BF16 kernels, and cuDNN ships a tuned BF16 fused-attention engine that builds without complaint on sm_121. There is no gap to fill here, and the numbers say so.</p>
<figure id="ptx-original-03"><a href="/images/consumer-blackwell/ptx-original-03.png" aria-label="Open full-size figure"><img src="/images/consumer-blackwell/ptx-original-03.png" alt="BF16 flash attention, same box and session, B=2 H=32 D=128 non-causal. Our hand-PTX V21 loses to both the CuTe DSL kernel and the vendor library, and the gap is occupancy, not structure: it closes from 0.61x to 0.92x of flash-attn as the sequence grows and the large per-CTA tile finally has enough work to amortize.</figcaption></figure>
<p>Our V21 loses, and it is worth being precise about how, in the same absolute terms the win got. On the same box and session (B=2, H=32, D=128, non-causal) V21 sustains 46.1 TFLOPS at S=2048, 67.9 at S=4096, and 74.6 at S=8192; the chart above sets those against the baselines. At short sequences that is well behind, 0.61× of flash-attn at S=2048. The gap is occupancy, not a property of hand-written PTX. V21 carries a large per-CTA tile to keep the MMA fed (82 KB of shared memory, which is most of the 99 KB SM), so it runs one block per SM, and at small problem sizes there isn&#x27;t enough work to amortize the launch and pipeline-fill cost across that one block. As the sequence grows the kernel gets the work it wants and the gap closes steadily, to 0.92× of flash-attn and 0.83× of cuDNN at S=8192. The production traffic that matters is long-context, and there V21 lands within roughly ten percent of the mature CuTe-DSL kernel and within twenty of the vendor library, both of which have had years of tuning.</p>
<p>I tried to close it by hand, and the two levers that didn&#x27;t work are the useful part. First, register double-buffering of the <code>ldmatrix</code> loads, which prefetches the next tile&#x27;s operands into registers while the current MMA runs. The PTX I wrote for it produced <em>identical SASS</em> to what I already had; <code>ptxas</code> was already scheduling that prefetch, and my &quot;optimization&quot; was a no-op the compiler had beaten me to. Second, a smaller tile to raise occupancy: half the shared-memory footprint, two blocks per SM, double the occupancy. It ran 12% <em>slower</em>, because the smaller tile feeds the MMA less efficiently and the occupancy gain didn&#x27;t pay for the throughput loss. Then I built the thing those two failures pointed at, V22, a four-buffer software-pipelined kernel that overlaps loads and MMA across four stages by hand. It worked, in that it beat V3, but it landed short of V21 and far short of the compiler. I wrote a more sophisticated kernel and it still lost to CuTe DSL&#x27;s auto-generated pipeline. The conclusion is that closing this gap needs the full async-multi-stage machinery the compiler emits for free, and that may simply not be reachable by hand under the 99 KB shared-memory and warp-level-<code>mma.sync</code> constraints. It is also not worth it, because the FP8 kernel is the one production runs and the one the toolchain can&#x27;t provide.</p>
<p>That is the other half of the thesis. Hand-written PTX does not beat a mature toolchain at its own game; it ships the kernel the toolchain hasn&#x27;t shipped yet. BF16 attention is not that kernel. FP8 attention, on this chip, still is.</p>
<h2 id="gemm-a-second-optimization-journey">GEMM: A Second Optimization Journey</h2>
<p>Flash attention got the headline, but the same arc played out in GEMM, and it&#x27;s worth telling because the two endpoints land on opposite sides of the thesis again.</p>
<figure id="ptx-original-04"><a href="/images/consumer-blackwell/ptx-original-04.png" aria-label="Open full-size figure"><img src="/images/consumer-blackwell/ptx-original-04.png" alt="Two GEMM journeys at 4096^3. <p>The FP8 GEMM is the FP8-attention story again, for the same reason. CUTLASS&#x27;s CuTe DSL can&#x27;t lower the FP8 MMA on SM120 (<a href="https://github.com/NVIDIA/cutlass/issues/3044">#3044</a> blocks GEMM exactly as it blocks attention), so there is no compiler-generated FP8 GEMM to lose to. Hand-written, the kernel climbed from 13 TFLOPS naive to <strong>65 TFLOPS</strong> at 4096³, a 5× gain and 26% of the measured FP8 tensor peak. The hand-PTX-fills-the-gap pattern isn&#x27;t specific to attention. It follows the FP8 instruction the toolchain can&#x27;t emit, wherever that instruction is needed.</p>
<p>The BF16 GEMM is the mature-instruction story again, and its last useful win is my favorite small result in the library. The best BF16 GEMM (<code>v3</code>, a 128×128 tile) capped at ~48 TFLOPS, occupancy-bound. The rewrite (<code>v5</code>, a 128×256 register-blocked tile carrying 64 FP32 accumulators per thread) had more arithmetic per CTA but ran <em>one block per SM</em> at 168 registers per thread, and at 4096³ it initially <em>regressed</em>, because the bigger tiles thrashed the L2. The fix wasn&#x27;t in the math at all. It was a <strong>threadblock swizzle</strong>: change the order in which CTAs are assigned to output tiles, so that CTAs running concurrently touch nearby regions of the input matrices and hit in L2 instead of evicting each other. That single reordering lifted the L2 hit rate from 87% to 94% and turned the regression into a clean win: 54.7 TFLOPS at 4096³ under an L2 flush (53.7 warm; v5 is warmth-insensitive), the new BF16 GEMM best in the library, and +31% over v3 flushed-for-flushed (54.7 vs 41.8). Warm-for-warm the gap is +17% (53.7 vs 46.0); the flush widens it because v3&#x27;s warm number was the one inflated by cross-iteration residency. Same lesson VT-GMEM taught in FP8: <strong>the win was where the data went, not what the math did.</strong> I changed which core computed which tile, and nothing else, and the kernel got 16% faster.</p>
<p><code>v5</code> ships bit-identical to <code>v3</code> (the swizzle is a scheduling change, not a numeric one, so it preserves the deterministic-build guarantee), routed in only at the large shapes where it wins; the production prefill shape stays on <code>v3</code>. And it&#x27;s still occupancy-bound at one block per SM, the same wall as everything else here, which the roofline section makes general.</p>
<h2 id="gdn-in-ptx-and-the-bug-i-caught-on-myself">GDN in PTX, and the Bug I Caught on Myself</h2>
<p>The model these kernels serve is a hybrid, and most of its layers are not attention at all: three quarters of them are gated delta-net (GDN), a linear-attention variant that carries a fixed-size recurrent state instead of a growing KV cache, with a full-attention layer every fourth. To serve such a model from hand-written PTX I had to write GDN kernels too: a chunked-prefill kernel that scans the prompt, and a decode kernel that advances the recurrent state one token at a time. As far as I can tell these are the first hand-written PTX GDN kernels for SM12x. The implementations I know of are CUDA C++ (the other open GB10 inference engine ships a GDN/Mamba-2 kernel) or Triton (the flash-linear-attention library&#x27;s chunk-GDN, and NVIDIA&#x27;s reference Gated DeltaNet, written for Hopper&#x27;s WGMMA). None of them is hand-written PTX. That&#x27;s the cut I&#x27;m claiming, not that nobody has run GDN on this chip.</p>
<p>The decode kernel is a recurrent state update and it profiles like one. At serving batch (128 sequences, 32 value heads, a 128×128 state per head) it sits at 86% of the memory pipe and 5% of the tensor pipe: almost no math, just moving state in and out. Useful bandwidth lands near 60 GB/s, well under the 273 GB/s ceiling, because the 128×128 recurrent-state access doesn&#x27;t coalesce cleanly, and it hits the same occupancy wall as everything else here, with the state tile pinning it to one block per SM at about 8% occupancy. It is correct and it&#x27;s the first of its kind on this chip, but I would not call it optimized. The headroom is in the access pattern, and I haven&#x27;t chased it. The more useful part of this section is the bug.</p>
<p>During one of my kernel audits, checking each kernel against its Hugging Face reference, the GDN pair didn&#x27;t line up. The recurrence at each step is a gated delta rule: the new state is the old state plus an outer-product correction, <code>S&#x27; = S + β·k·(v − α·(S·k))ᵀ</code>, where α is the per-step gate decay and β the write strength. The decode kernel applied the gate decay before the state update (its inner term was <code>v − α·(S·k)</code>), matching Hugging Face&#x27;s <code>recurrent_gated_delta_rule</code> to tolerance zero. The prefill kernel computed <code>v − (S·k)</code>. Same recurrence, two implementations, and only one was right: prefill was missing the α factor, on every GDN layer of every prompt.</p>
<p>It survived because the tests couldn&#x27;t catch it. Both kernels had golden-vector tests and both passed, but the golden vectors had been generated with the same no-alpha math the prefill kernel used. The test for the buggy kernel encoded the bug. The decode test passed for a different reason: it checks a single token, where one step of missing decay stays under tolerance. So the suite was green over a real, production-served discrepancy. <strong>The test can encode the bug.</strong> A golden vector is only as correct as the reference that produced it, and &quot;all tests pass&quot; means &quot;consistent with my assumptions,&quot; not &quot;correct.&quot;</p>
<p>Then the question every engineer should ask: how wrong, actually? On the synthetic golden inputs the divergence looked catastrophic, 500% on one shape and 6000% on another, because those inputs use unbounded random keys and the per-step error compounds through the recurrence. But production l2-normalizes the keys and queries before the GDN layer, which bounds the per-step error, and the gate decay is contractive, so it doesn&#x27;t run away: measured on normalized inputs it is about 0.1 to 0.6% mean relative error on the output, and it plateaus with sequence length rather than growing. That is why the model served at its target quality with the bug present and passed end-to-end byte-identity validation. The bug was real and the bug was small, and both are true at once.</p>
<p>The fix is one instruction (the same gate-decay multiply the decode kernel already has, mirrored into prefill), plus regenerating both golden vectors from the Hugging Face math and tightening the tolerances so they can actually tell the two recurrences apart. I built and validated the corrected kernel against the HF reference but did not flip it on by default, because changing prefill changes the state the model ingests, which changes served output, so it&#x27;s gated behind a flag pending a quality re-eval. Found, measured, fixed, gated, not yet deployed.</p>
<p>I include it because the alternative, quietly correcting it and never mentioning it, is how a library&#x27;s numbers stop meaning anything.</p>
<p>That audit taught two more things worth passing on, both about not trusting the wrong tool. The static-analysis pass over the kernels flagged several shared-memory <em>races</em>: a P-store aliasing a K-read with an insufficient barrier in the prefill kernel, and a write-after-read on the GDN query buffer. Read by eye, they looked real. Run under <code>compute-sanitizer --tool racecheck</code>, every one came back with <strong>zero hazards</strong>. The races weren&#x27;t there; the static reading couldn&#x27;t see the barrier that made them safe. On a chip with no SASS assembler, the hardware tools (racecheck, synccheck, memcheck) are the ground truth, and code-reading is a hypothesis generator, not a verdict. The second thing was dumber and cost more time: a batch of tests &quot;failed&quot; in a way that looked like a cross-test state leak, and I chased it as a kernel bug for an afternoon before finding that the test runner had picked a <em>months-stale binary</em> (it sorted the build hashes alphabetically and grabbed an old one). Selecting the newest binary by mtime, everything passed. The phantom bug was in my harness, not my kernel. Lesson filed: select test binaries by mtime, and suspect the environment before the kernel.</p>
<h2 id="the-library-also-trains">The Library Also Trains</h2>
<p>Everything above is inference. But the same chip runs fine-tuning too, and a serving-only kernel library would mean training falls back to the slow path on the very hardware meant to run it fast. So the backward pass is hand-PTX too, and correctness there matters more than anywhere else: training kernels are where a quiet numerical error becomes a model that subtly won&#x27;t converge.</p>
<p>The backward surface is 1:1 with the forward one: backward flash attention across causal, GQA, varlen, paged, and FP8-KV, with dQ/dK bit-exact against PyTorch autograd and dV within the BF16 noise floor (its reduction runs over the whole sequence in a different order than autograd&#x27;s, so it lands within noise rather than bit-for-bit); backward GEMMs that hit 21× forward, 22.6× backward, and 11.8× on a full step over the scalar reference, by routing the backward through the same MMA path as the forward kernels via a transpose. That scalar reference is the library&#x27;s own non-tensor-core implementation, the one each kernel is validated against, not a tuned vendor library, so these are MMA-versus-naive ratios.</p>
<figure id="ptx-original-05"><a href="/images/consumer-blackwell/ptx-original-05.png" aria-label="Open full-size figure"><img src="/images/consumer-blackwell/ptx-original-05.png" alt="The training kernels route the backward pass through the same MMA path as the forward kernels (via a transpose), for 21× on the forward GEMM, 22.6× on the backward, and 11.8× on a full training step over the scalar reference (the dashed line at 1×), while staying bit-exact: dQ/dK match PyTorch autograd, AdamW&#x27;s weight is bit-exact to a reference, LAMB within 1.9e-9 of an f64 reference." loading="eager" width="1170" height="600" /></a><figcaption>The training kernels route the backward pass through the same MMA path as the forward kernels (via a transpose), for 21× on the forward GEMM, 22.6× on the backward, and 11.8× on a full training step over the scalar reference (the dashed line at 1×), while staying bit-exact: dQ/dK match PyTorch autograd, AdamW&#x27;s weight is bit-exact to a reference, LAMB within 1.9e-9 of an f64 reference.</figcaption></figure>
<p>On top of that sit the optimizer and quantization kernels a real training loop needs: AdamW with a BF16 weight and FP32 master copy (weight bit-exact to a reference given identical gradients; the optimizer step is bit-exact, not training end to end, since the dV feeding it only lands within the BF16 noise floor; the moments within one or two ULP), LAMB (within 2e-9 of an f64 reference), QAT fake-quant for FP8 e4m3 both per-tensor and per-channel with a straight-through-estimator backward, and the gradient plumbing (FP32 accumulation, L2-norm clipping, a loss scaler). Dozens of training tests gate it, and the end-to-end demos close real loops: a single linear layer drops its loss 183× over 50 AdamW steps, a two-layer MLP 11×. None of this is glamorous and none of it is a headline TFLOPS number. It&#x27;s the half of the library that&#x27;s easy to skip and expensive to skip wrong.</p>
<h2 id="the-long-tail-is-most-of-the-library">The Long Tail Is Most of the Library</h2>
<p>Everything above is the highlight reel, the kernels with the best arcs. But those flagships are five kernels (the two flash-attention kernels, the two GEMMs, and GDN decode) out of close to <strong>280</strong>, and a library is judged on its coverage, not its best kernel. The other 275 are not filler and they&#x27;re not auto-generated; each family below was a design problem I had to think through, and the thinking is the point. So rather than list them, here is how the bulk of the library was reasoned out, family by family.</p>
<figure id="ptx-original-06"><a href="/images/consumer-blackwell/ptx-original-06.png" aria-label="Open full-size figure"><img src="/images/consumer-blackwell/ptx-original-06.png" alt="The 280 hand-written kernels by family (an exhaustive bucketing of the .visible .entry points). <h3>Attention Is a Grid, and Every Cell Is a Decision</h3>
<p>The flash-attention surface is a cross-product of dtype and variant (91 of the 280 kernels), because a single serving model hits most of the cells at once:</p>

<p>The reason this is 91 kernels and not one parameterized monster is that a few design decisions recur and each forces a real fork. All of it is built on the SM80 instruction base, because SM121 has no <code>tcgen05</code>, so the tiles had to be re-budgeted for the 99 KB SMEM (the SM80 base assumes ~64 KB, SM90 assumes 228 KB, and neither fits). Split-KV had to keep its partial sums in <strong>FP32</strong>, not FP16, because the FP16 combine drifts observably on long sequences once you&#x27;re adding many splits. Paged KV uses <strong>non-TMA scatter/gather</strong>, because TMA&#x27;s contiguous descriptors can&#x27;t express a per-page address computation. You do the page-table lookup in code and <code>cp.async</code> the transfer. None of these is visible in a feature checkbox, and all of them are the actual work.</p>
<h3>Linear-Time Sequence Models: The State Is the Design</h3>
<p>Not every layer is attention. GDN and Mamba-2 carry a fixed-size recurrent state instead of a growing KV cache, and that single fact drives the whole family (21 kernels). The decode kernel advances the state one token at a time, which is memory-bound, as the flagship GDN section showed. Prefill is where the design choice lives: you can run the recurrence sequentially (O(L), simple, slow) or as a chunked scan that does the within-chunk work in parallel and only carries the state across chunk boundaries. The library ships the chunked scan, because prefill throughput is what a long prompt actually waits on. Around the recurrence sit the pieces the gated and SSM layers need: the short causal <code>conv1d</code>+SiLU that precedes the gate (its own fused kernel, forward and backward, and a chunked variant so prefill doesn&#x27;t serialize on it), and gated-RMSNorm-SiLU, which fuses the norm, the gate, and the activation into one pass so the activations never round-trip to HBM. The guiding rule across this family is the same one VT-GMEM taught: on a bandwidth-bound chip, fuse until the intermediate tensors never leave the SM.</p>
<h3>The GEMM Dtype Ladder: Pick the Format by the Bound</h3>
<p>The 51 GEMM/GEMV kernels look like redundancy until you notice they&#x27;re a ladder of precision-versus-bandwidth tradeoffs, and a real model picks a rung by its bottleneck. BF16 is the reference and the training path. W8A16 (BF16 activations, FP8 weights, dequantized in SMEM after load) is the bandwidth win for dense decode, where you&#x27;re weight-bound and halving the weight bytes directly buys tokens. W4A16 goes further on paper, but as the negative-results section covers, the 4-bit dequant tax can exceed the bandwidth saving and flip the kernel compute-bound, so it&#x27;s a rung you take only when the shape supports it. Grouped per-expert GEMM (BF16, FP8, MXFP4) is the MoE case, where each expert is a small matmul and the win is batching them; its fastest variant reaches 11.1 TFLOPS, low in absolute terms precisely because those per-expert matmuls are small, so the gain is in batching many tiny GEMMs rather than peak throughput. And 4-bit is the top of the ladder. SM121 has a genuine NVFP4 MMA (<code>kind::mxf4nvf4</code>: e2m1 elements with an FP8 E4M3 scale per 16, which is what makes it NVFP4 rather than MXFP4&#x27;s E8M0 scale per 32), and the microbench puts that instruction at 493 TFLOPS, the 4× roofline line. The library has a dense NVFP4 GEMM that is correct against the reference; closing the gap from correct to that ceiling is where the next post&#x27;s headroom lives. CUTLASS exposes SM120 NVFP4 only through a sparse C++ example, with no CuTe-DSL dense kernel, so this is one more thing the toolchain won&#x27;t generate for you. The thought process across the whole ladder is one sentence: quantization is never free, and you choose the format by which wall you&#x27;re against.</p>
<h3>Quantization, the Unfashionable Half of Quantization</h3>
<p>Sixteen kernels just convert between formats, and they exist because every model family standardizes on a different one (FP8 1×128 block-scaled, NVFP4, MXFP4, MXFP8), and you cannot load a real checkpoint without the matching quant and dequant. The design choice that recurs here is to <strong>fuse the quantize with the store</strong> (quantize and write in a single kernel rather than materializing the high-precision tensor first), and to lay the block scales out so the consuming GEMM reads them without a gather. Unglamorous, load-bearing, and the reason the GEMM ladder above can actually be fed.</p>
<h3>The Supporting Cast: Required, Fused, Numerically Fussy</h3>
<p>Forty-odd kernels are the parts no blog post leads with and no model runs without: RMSNorm, RoPE, SiLU/GeLU, embedding lookup, cross-entropy (forward and backward), top-k/top-p sampling, the split-K flash-decoding combine. The design thread through them is fusion and numerical care: gated-RMSNorm-SiLU is three ops in one kernel, the norms accumulate in FP32 even with BF16 I/O, the softcap is its own fused variant because bolting it on afterward costs a pass, and the sampling path got the multi-block masked-argmax optimization because at decode every microsecond is on the critical path. They&#x27;re a long list precisely because correctness here is cheap to get almost-right and expensive to get exactly right.</p>
<h3>The Frontier Primitives: Built Ahead of Need</h3>
<p>A handful of kernels exist because the next wave of models will want them, not because anything in production needs them today: a DSA-style sparse-attention indexer (the learned top-k position selector the newest DeepSeek-class models use), the NSA selection pipeline, and an Engram conditional-memory lookup (multi-head hashing plus a gated table read) that, as far as I know, nobody else has written for SM12x. These are correctness-validated reference kernels, deliberately not optimized; I&#x27;m listing them as coverage and as intent, not as wins.</p>
<h3>Two Honest Qualifiers</h3>
<p>First, the test gate: every one of these is checked against a PyTorch golden vector, 184 of them across more than 500 tests, so &quot;it exists&quot; means &quot;it matches the reference numerically,&quot; not &quot;it compiles.&quot; Those goldens are generated in a separate process from stock PyTorch and Hugging Face reference ops, not from the kernel&#x27;s own output. The GDN bug is the honest asterisk on that: for a kernel whose reference is a novel recurrence, the golden is only as good as your derivation of it, and GDN&#x27;s derivation was wrong. Where a stock library op exists (the norms, activations, softmax, GEMMs) the reference is unambiguous; the residual risk lives in the handful of novel-recurrence kernels, and the fix the GDN case forced is to validate those against the reference model&#x27;s own function (HF&#x27;s <code>recurrent_gated_delta_rule</code>), not a hand-derivation. Second, the perf is tiered: the flagships (FP8/BF16 FA, the GEMMs, GDN decode) are MMA-optimized and carry the numbers in this post; most of the long tail (MLA, Mamba-2, the sparse and frontier kernels) is correctness-validated at reference speed, with MMA optimization tracked but not yet done. Coverage first, then speed where it pays.</p>
<p>One long-tail kernel earned a real perf story, so it gets one: <strong>MLA decode with split-K, up to 7.54× over scalar.</strong> Multi-head latent attention has a decode problem: a single user&#x27;s one query token can&#x27;t fill 48 SMs, so most of the machine idles. FlashDecoding splits the KV reduction across SMs and combines the partials, worth up to <strong>7.54×</strong> at single-user long-context (16-way split), byte-exact to the scalar reference. The split count drops as batch and head count grow, because once the SMs are busy there&#x27;s nothing left to split for. And it had its own dead end: an earlier variant that packed 16 heads per CTA to share the compressed-KV load ran <strong>7× slower</strong> (too many registers per CTA, occupancy collapsed) before the split-K-plus-MMA design (a 4.5× rewrite of the inner GEMM) turned it around.</p>
<p>The point of the list isn&#x27;t the individual figures. It&#x27;s the difference between shipping one fast kernel and shipping the kernels a model actually needs, and this library is the second.</p>

FP8 FA and BF16 FA are limited by shared memory (45 KB and 82 KB of the 99 KB SM); GEMM v5 by registers (168 per thread for its accumulator tile, with zero shared memory); GDN decode by its recurrent-state tile. Datacenter Blackwell escapes this with tcgen05 and tensor memory, which hold accumulators off the register file and the SMEM budget. SM121 has neither.</figcaption></figure>
<p>GEMM v5 is pinned by register pressure (168 registers per thread for its 128×256 accumulator tile, with zero shared memory), so it gets one block per SM at 15% occupancy. The flash-attention kernels are pinned by shared memory instead: V21&#x27;s 82 KB tile and V12c&#x27;s 45 KB tile each leave room for only one or two blocks in the 99 KB SM. GDN is pinned by its state tile. Same wall, four doors to it. Datacenter Blackwell walks around the wall with <code>tcgen05</code> and tensor memory, which hold the matmul accumulators in a separate memory space, off the register file and out of the shared-memory budget, so a kernel can carry a big accumulator tile <em>and</em> keep occupancy up. SM121 has neither. So the gap to the tensor peak is a hardware wall (no TMEM to offload accumulators), not a tuning miss, and <strong>knowing which wall you&#x27;re against</strong> is what kept me from spending another month chasing a few percent the silicon will not give up.</p>
<p>Two more walls, briefly. The BF16 attention gap is the one above: the compiler&#x27;s async-multi-stage pipeline beats hand PTX and I couldn&#x27;t close it by hand. And several earlier flash-attention variants (V8, V11, V12) use more than 90 KB of dynamic shared memory and crash on the Spark after the unified memory fragments. That is a platform limitation, not a kernel bug, with V21 (82 KB) as the production replacement. I note it because someone will try those variants and hit it.</p>
<h2 id="determinism-at-the-kernel-level">Determinism at the Kernel Level</h2>
<p>This part is not novel. Thinking Machines Lab&#x27;s <a href="https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/"><em>Defeating Nondeterminism in LLM Inference</em></a> (Horace He, September 2025) is the reference for the root cause: batch-size variance in the core kernels, not GPU concurrency, is why the same prompt yields different tokens run to run, and batch-invariant ops fix it. vLLM ships those ops mainline now, and a follow-on paper (<a href="https://arxiv.org/abs/2511.17826">Zhang et al., 2025</a>) demonstrated deterministic, bitwise-reproducible inference through vLLM and validated it on, among other GPUs, an RTX PRO 6000, which is consumer Blackwell (sm_120). So the concept is settled, and it has already been shown on this class of hardware through the framework&#x27;s Triton kernels. So the result and the concept are theirs, and it&#x27;s worth being precise about what is and isn&#x27;t new here rather than dressing it up. This library doesn&#x27;t run on that stack (the serving path is hand-PTX with no framework underneath), so the batch-invariant reduction had to be re-implemented at the kernel level rather than inherited from vLLM. That&#x27;s an implementation-layer point, not a new result: the same guarantee, rebuilt where this stack actually lives.</p>
<p>The non-determinism that mattered here lived in the split-K GEMM. When the reduction over K is split across blocks and combined with atomic adds, the summation order depends on scheduling and batch position, so the low bits of the logits move, and with sampling that flips tokens. Under <code>SPARK_DETERMINISTIC=1</code> the library swaps in a split-K with a fixed reduction order and captures the deterministic kernels in a CUDA graph (the capture matters: it pins the launch order, which is the other source of run-to-run drift).</p>
<p>The result, on a fixed serving configuration: 16 identical seeded requests that produce 14 distinct completions by default collapse to <strong>1</strong> with the flag on, and greedy output is character-identical run to run. The cost is small. The deterministic split-K started at 1.66×, CUDA-graph capture removed a residual 14%, and the steady-state decode penalty is now about <strong>3%</strong> (82.0 to 84.5 ms/token), and it holds up under repetition: across five paired runs it is <strong>3.0% ± 0.6%</strong> (the ± is the sample standard deviation over the five pairs, not a standard error or a bound). That is a within-session paired measurement (deterministic on versus off, back to back), not a cross-session comparison. The ±5% band elsewhere in this post is run-to-run clock drift between separate sessions, which cancels in a paired A/B, so a 3% paired delta is cleanly resolvable (its own spread is 0.6%) where a 3% gap between two independently-timed kernels would not be. Bit-exactness for roughly the price of nothing is the point: it&#x27;s what makes RL rollouts and evals reproducible, which is the whole reason to run a model on hardware you control.</p>
<p>One boundary worth stating. The guarantee is per serving configuration. The serial and batched paths sample through slightly different code, so a given seed can produce different output depending on which path served it; each path is individually bit-exact. Closing that cross-path gap is a serving cleanup, not a kernel-determinism question, and I haven&#x27;t done it.</p>
<h2 id="what-didn-t-work-kept-on-the-record">What Didn&#x27;t Work, Kept on the Record</h2>
<p>Scattered through the post are dead ends, and I want to collect a few more in one place, because the negative results are the part a kernel engineer can actually use: they&#x27;re the experiments you don&#x27;t have to re-run.</p>
<ul><li><strong>CUDA-graph capture of a mixture-of-experts FFN: −15%.</strong> Graphs remove kernel-launch overhead. But that FFN is weight-bound: the bottleneck is reading the expert weights from memory, and the launch overhead was already hidden behind the GPU&#x27;s async pipelining. Capturing it added graph overhead and removed nothing on the critical path. (The same capture <em>is</em> a win on a smaller, less weight-bound MLP, which is the whole point: the technique isn&#x27;t good or bad in the abstract, it&#x27;s good or bad <em>for a given bound</em>.)</li><li><strong>4-bit weights for a dense MLP: −16%.</strong> Swapping W8A16 (8-bit weights) for W4A16 NVFP4 (4-bit) should, on paper, halve the weight bandwidth. It ran slower, because the 4-bit dequant (unpack the nibble, apply a per-16-element FP8 block scale) costs more compute than the bandwidth it saves at that shape, flipping the kernel from bandwidth-bound to compute-bound. Lower precision is not automatically faster; the dequant tax is real and shape-dependent. And the existing test only checked correctness, so nothing flagged the regression, the same blind spot as the GDN goldens in a different costume.</li><li><strong>Self-speculative decoding that helped the base model but not the fine-tuned one.</strong> MTP-style draft heads gave the base model roughly 1.1× on decode and the fine-tuned adapter roughly 1.0×. The heads had learned the base model&#x27;s next-token distribution; after fine-tuning shifted that distribution, the draft acceptance rate fell far enough to erase the gain. A speedup measured on the base model is not a speedup you&#x27;ve earned on the model you actually serve.</li></ul>
<p>The unifying read across these and the <code>performance_audit</code> negatives is consistent: on SM121a, for the batch-1, moderate-shape regime, occupancy and tensor-core saturation move the needle and memory-pipeline depth tricks mostly don&#x27;t. That&#x27;s a property of this chip, and the only way to know it was to measure the things that didn&#x27;t work.</p>
<h2 id="what-the-journey-taught-me">What the Journey Taught Me</h2>
<p>The named lessons, collected, because they&#x27;re the part that transfers to anyone doing this on a new chip:</p>
<ul><li><strong>Layout beats scheduling, twice.</strong> In FP8 attention, versions V3 through V11 improved how work was scheduled (10 to 30 TFLOPS); one change to how the data was laid out (VT-GMEM) did 30 to 108. In BF16 GEMM, the last win was a threadblock swizzle (changing which core computes which tile, not the math) for a 16% gain via L2 reuse. On a chip where the tensor cores are fast and the memory system is the constraint, where the bytes land matters more than when they move.</li><li><strong>The optimization the profiler points you toward can be wrong; it tells you the truth but not the inference.</strong> Nsight correctly flagged the VT-GMEM bank conflicts; removing them cost 2.3-3.2× because the conflicted layout was the one the MMA wanted. The metric was a fact; the fix was a false hypothesis.</li><li><strong>TMA is not free.</strong> A bulk copy with no compute to overlap is a slower load. TMA paid only once warp specialization gave it something to hide behind.</li><li><strong>The test can encode the bug.</strong> The GDN golden vectors validated the buggy recurrence because they were generated from the same wrong math. &quot;All tests pass&quot; means consistent with your assumptions, not correct. Check goldens against an independent reference.</li><li><strong>Measure the real magnitude before you panic or relax.</strong> The GDN bug looked like 6000% error on synthetic inputs and was 0.1-0.6% in production once the inputs were normalized. Same bug, two conclusions; only the production-realistic one mattered.</li><li><strong>Don&#x27;t benchmark over training.</strong> An early FP8 re-measurement read 48 TFLOPS at S=8192; the real number on a free GPU was 108. The difference was a training job eating the shared 273 GB/s memory bus. On unified-memory hardware the GPU benchmark and everything else on the box are fighting for the same bytes, so measure clean or don&#x27;t measure.</li><li><strong>Know which wall you&#x27;re against.</strong> Occupancy walls you can sometimes tune around; a missing hardware feature (no tcgen05/TMEM) you cannot. Drawing the line honestly is what stops you from burning a month on a few percent the silicon won&#x27;t give up.</li><li><strong>A more sophisticated kernel doesn&#x27;t automatically beat the compiler.</strong> The hand-written 4-buffer BF16 pipeline (V22) was more elaborate than the kernel that beat it. Effort isn&#x27;t throughput. Where the toolchain is mature, it usually wins, and the honest move is to use it.</li><li><strong>Lower precision isn&#x27;t free, and graphs aren&#x27;t free.</strong> The 4-bit dequant tax and the weight-bound graph regression are the same shape of mistake: an optimization that looks right in the abstract, applied where its precondition (bandwidth-bound, launch-bound) doesn&#x27;t hold. Check the bound before the technique.</li><li><strong>Verify with the hardware tool, not static analysis.</strong> Code-reading flagged races that <code>racecheck</code> proved weren&#x27;t there. On a chip with no SASS assembler, the sanitizers are the ground truth and a code review is a hypothesis. And the environment lies too: a stale test binary and a near-OOM page cache both produced phantom &quot;kernel bugs.&quot; Suspect the box before the kernel.</li></ul>
<p>And the one that carried over from the upstreaming work: read the source, and reproduce a known-good baseline before you trust a new measurement. Most of the time I lost on this project was lost to trusting a number I hadn&#x27;t earned.</p>
<h2 id="how-these-numbers-were-measured">How These Numbers Were Measured</h2>
<p>Every TFLOPS and GB/s figure in this post comes from the same harness on the same machine, and the methodology is worth stating plainly, because GB10 has one wrinkle that changes how you have to report.</p>
<p>The hardware is a single NVIDIA GB10 (DGX Spark), compute capability sm_121a, 48 SMs, 273 GB/s unified LPDDR5x, boosting to 3.0 GHz. The software is CUDA 13.0 (ptxas V13.0.88), driver 580.126.09, and cuDNN 9.19 for the cuDNN baselines. Kernels are timed with CUDA events (<code>cudaEventRecord</code> around the launch, <code>cudaEventElapsedTime</code> after a sync), 5 warm-up iterations discarded, then 200 measured iterations for flash attention and 100 for GEMM, with the median reported. One caveat to state rather than bury: the timed iterations reuse the same operand buffers and the harness does not flush L2 between them, so absolute throughput carries some cross-iteration cache warmth, most visible in the GEMM numbers whose whole story is L2 reuse. The relative swizzle win (v5 over v3) is largely robust to it, since the warmth is common-mode across both, and the 87%-to-94% L2 hit-rate figure comes from a single profiled Nsight Compute launch rather than the loop. I then measured the warmth directly: re-running with an L2 flush before each timed launch (a memset larger than L2, outside the timed window) barely moves v5, which is compute-bound at about 40% of the tensor-core speed-of-light so cache state has little leverage on it, and drops the un-swizzled v3 about 9%, so the swizzle win actually widens under a cold cache, from roughly +17% to +31%. The warm benchmark understated the swizzle rather than inflating it. Flash-attention TFLOPS is <code>4·B·H·S²·D / latency</code> (the two matmuls, QKᵀ and PV, at two FLOPs per multiply-accumulate); GEMM is <code>2·M·N·K / latency</code>. The tensor-core ceilings (123 / 246 / 493) come from a separate register-resident MMA microbench, compiled with <code>nvcc -gencode arch=compute_121a,code=sm_121a</code>, where the operands already live in registers so the loop measures pure issue rate rather than anything memory can throttle.</p>
<p>The wrinkle is the clock. GB10 does not expose application-level clock locking; <code>nvidia-smi -lgc</code> has no effect on this consumer part, so I cannot pin the SM clock the way you would on a datacenter GPU. Instead I warm each kernel to a steady thermal and clock state before timing and report medians, and that is why every number in this post carries a &quot;~&quot;: run-to-run clock drift is real on this hardware, so the figures are steady-state medians rather than single pinned numbers. Across repeated benchmark runs the medians reproduce to within about ±5%, the residual coming from that clock drift, page-cache state, and whatever else on the box is sharing the memory bus, which is wide enough that a gap of a few percent between two kernels is not by itself meaningful.</p>
<p>Baselines were measured on the same box in the same session. The spark-kernels numbers reproduce from <code>cargo run --release --example benchmark</code>. The cuDNN and flash-attn <a href="https://github.com/Dao-AILab/flash-attention/pull/2634">#2634</a> figures come from their own harnesses (<code>scripts/bench_cudnn_fp8_fa.py</code> and <code>scripts/bench_fa4_bf16_fa.py</code>) and are point-in-time references on this GB10 rather than something you can regenerate from this repo. Correctness is the 184 golden vectors checked against PyTorch references, and the kernels run clean under <code>compute-sanitizer --tool memcheck</code>.</p>
<h2 id="using-it">Using It</h2>
<p>The library is open source. It builds with <code>cargo build --release</code>; the only runtime dependency is <code>libcuda.so</code> from the driver, so there&#x27;s no CUDA toolkit to install. Every TFLOPS number in this post comes from <code>cargo run --release --example benchmark</code>, and the correctness gates are <code>cargo test</code> (the kernels are checked against 184 PyTorch golden vectors across more than 500 tests). If you&#x27;d rather not touch the host toolchain at all, the Dockerfile builds a 132 MB image (Ubuntu plus the binary, no CUDA toolkit baked in) that runs the kernels through <code>docker run --gpus all</code>.</p>
<p>These kernels don&#x27;t run in a vacuum. They compose into a serving path that, on this hardware, runs meaningfully faster than going through the stock open-source framework backends, which is the entire reason to write them rather than wait for the toolchain. That end-to-end story, the scheduler and batching and quantization choices that turn fast kernels into fast serving, is a separate post.</p>
<p>For provenance and related work: the foundational SM120/121 flash-attention kernels were upstreamed into the flash-attention library (PRs <a href="https://github.com/Dao-AILab/flash-attention/pull/2329">#2329</a> / <a href="https://github.com/Dao-AILab/flash-attention/pull/2330">#2330</a> / <a href="https://github.com/Dao-AILab/flash-attention/pull/2333">#2333</a>), which the broader ecosystem now builds on. That&#x27;s the previous post. The closest other open-source work on this chip is a CUDA-C++ inference engine, the Triton/PyTorch linear-attention and batch-invariance libraries, and an FP4 fused-attention kernel for SM120 that embeds its tensor-core MMA as inline PTX inside CUDA C++. This library is the whole-kernel hand-written-PTX cut: the same kernels, written one layer lower, for the seam where that pays. If your team is on consumer Blackwell and hitting the same walls, I&#x27;d like to hear about it. <code>blake@secondnaturecomputing.com</code>.</p>
<p>A note on tooling. These kernels were written with AI assistance. The architecture decisions, the debugging, and every number reported in this post were human-directed and human-verified. I mention it for the same reason I walked through the GDN bug: you should know how the work was made before you trust its results. &quot;Hand-written&quot; here is NVIDIA&#x27;s own term for it: authored directly in PTX, the virtual ISA, rather than generated from a higher-level language by a compiler or a DSL. <code>ptxas</code> still lowers that PTX to SASS, as it does for any kernel, so what is written by hand is the PTX, not the final machine code. It does not mean written without tools.</p>
